## Context

买卖点页（`Front/src/views/bsp/BspView.vue`）由服务端分页驱动，查询条件经 `GET /api/bsp` 下推到 `WebAPI/bsp_store.query_bsp()` 的同一 WHERE（`COUNT` 与分页共用），返回记录携带 `is_sure` 与 `ladder`。`ladder` 是 `bsp_index` 上的持久列，但存量行为 NULL，由 `bsp_ladder.ladder_of_legacy` 按 `is_sure` 兜底映射（`true` → `L4`，`false` → `L2`）后才回显——即列表里的级别有两个来源：列值本身与兜底映射。`bsp-ladder-change` 的 D4 已明确不回填存量行。

页面已有行级「加入监控」的真实实现（弹窗内股票/周期只读、买点时间可编辑、价格按 `getPriceAt` 联动、分组含行内新建），工具条的批量「加入监控」则只是存根。自选页（`WatchlistView.vue`）已落地批量加入监控，但其参数口径是**统一**级别/时间——因为自选行只是一只股票，没有周期与买卖点时间上下文。

关键约束来自监控侧的消费方式：`monitor_store` 在为 `source_type='chan'` 的监控行补齐买卖点上下文时，按 `(code, kl_type)` 回查 `bsp_index` 中不晚于 `monitor_start_time` 的最近一条买卖点。也就是说监控行登记在哪个周期上，决定了它对外声称自己在跟踪哪个买卖点。

另有一处既有缺陷约束了批量功能的实现基础：`BspRecord.id` 是 `(page-1)*page_size + idx + 1` 的行号占位（`routers/bsp.py`），而表格 `row-key="id"` 且开了 `reserve-selection`。行号在不同查询条件下会重复，于是切换筛选后「已选」集合会命中新结果里位置相同的另一批记录。行级加入监控不受影响，但任何批量提交都会把这个集合直接写进监控。

## Goals / Non-Goals

**Goals:**

- 让「级别」成为与周期/类型/方向/状态同构的一等查询条件，过滤在分页之前生效。
- 让工具条批量「加入监控」真正可用，且每条记录按自身周期与买卖点时间登记，使监控行的买卖点上下文回查能命中用户点选的那条信号。
- 顺带修掉 `reserve-selection` 与行号占位 id 组合造成的选择集串行问题。

**Non-Goals:**

- 不做级别筛选的左侧栏 facet 入口（需要为 4 个级别各发一次计数请求，与现有 2 次额外统计请求叠加，成本不成比例；工具栏下拉已覆盖「查询条件」语义）。
- 不做级别多选（与买卖点类型/方向/确认状态的单选形态保持一致）。
- 不做批量参数的统一覆盖开关（级别与起始时间由各行上下文决定，没有可统一覆盖的场景）。
- 不改变确认阶梯判定算法，不回填存量行的 `ladder`，不改变 `CChan` 及计算内核。
- 不做跨页多选的取价性能优化（见 Open Questions）。

## Decisions

### D1: 级别过滤下推到 SQL，用 `COALESCE` 表达式复刻兜底映射

条件以 `COALESCE(b.ladder, CASE WHEN b.is_sure THEN 'L4' ELSE 'L2' END) = %s` 加入既有 WHERE，`COUNT` 与分页共用。

理由是「级别」在列表里本就是列值与兜底映射的合成结果，若只匹配列值，按 `L4` 筛选会漏掉全部已确认的存量行，列表出现「明明显示 L4 却筛不出来」。把映射语义放进 SQL 是让它与列表回显保持同一口径的唯一无状态做法。

备选与否决理由：**回填 `ladder` 列**（一次 `UPDATE` 后即可用朴素 `b.ladder = %s`）——与 `bsp-ladder-change` D4「不回填」的决定冲突，且回填值会在下一次整套替换写入前长期伪装成真实判定结果；**应用层过滤**——必须先把过滤后的全量拉进内存才能算对 `total`，破坏既有「过滤下推 + 服务端分页」的契约。

### D2: 级别下拉不提供「未定级」选项

兜底映射的值域只有 `L4` 与 `L2`，不存在映射后仍为空的行，因此没有「未定级」桶可供筛选。给出该选项会让用户点出一个永远为空的筛选结果。选项集固定为「全部 + L4/L3/L1/L2」，顺序按判定顺序（L4 > L3 > L1 > L2）而非数值顺序，与级别列的语义排序一致。

### D3: 级别条件只放工具栏

页面现有惯例是「左侧栏 = facet 导航（方向、周期），工具栏 = 查询表单」，而周期恰好两边都有。级别选择只放工具栏：它本质是一个查询条件，而左侧栏若加 level facet，为了与方向的计数展示对称就需要额外 4 次请求。作为取舍记录在案，若后续确实需要一键切换再加。

### D4: 记录标识改为可稳定复现的复合键

`id` 由行号占位改为由记录自身字段拼成的字符串（`code`、`kl_type`、`autype`、`bsp_date`、`bsp_type`、`time_key`），恰好对应 `bsp_index` 已有的 `UNIQUE (code, kl_type, autype, bsp_date, bsp_type, is_buy, time_key)`，因此天然唯一且可复现。

备选与否决理由：**加自增 `id` 列**——需要 DDL、惰性 DDL 与迁移脚本三处同步，还要为存量行回填，代价远大于收益；**去掉 `reserve-selection`**——能消除串行，但同时也让跨页多选失效，而用户刚获得的级别筛选（「只看 L4」后逐页挑选）正需要跨页多选配合。

选择复合键的代价是 `BspRecord.id` 由 `number` 变 `string`，属前端内部契约变更（proposal 已标 BREAKING）。影响面已核实：`BspRecord` 的消费方只有 `BspView.vue`（仅用作表格 `row-key`）与 `NestingDrawer.vue`（不读 `id`），另有 mock 数据需要同步。

拼键选 `bsp_index` 的全部唯一键字段（含 `is_buy`，编码为 `B`/`S`），使 key 与表的 `UNIQUE` 约束同构——唯一性由数据库自身的约束保证，而不是依赖对字段编码的假设。

这条在实现时得到了证实：实测 `bsp_index` 中每个 `bsp_type` 都同时存在于 `is_buy=True` 与 `is_buy=False` 两侧（如 `1` 在两侧各约 9450 行），即 `bsp_type` 并不含方向位。当前数据下 `is_buy` 对唯一性并非必需（`time_key` 已把范围收窄到单根 K 线，同根同类型不会同时是买点和卖点），但把它纳入 key 才能让唯一性不依赖该观察。

### D5: 批量按各行自身上下文提交，而非统一参数

每条记录以 `kl_type = row.kl_type`、`monitor_start_time = row.bsp_date`、`entry_price = getPriceAt(row.code, row.kl_type, row.bsp_date)` 提交，分组为统一参数。

这是本设计里最关键的一条。监控行的买卖点上下文不是创建时冻结的，而是列表查询时按 `(code, kl_type)` 回查 `bsp_index` 得来的（见 Context）。若照搬自选页做统一级别，用户在 30分 图上选中的买点会被登记成日线监控，之后列表回查到的是日线上的另一条买卖点或兜底空值——用户看到的与自己点选的不是同一条信号。按行提交则让回查精确命中用户点选的那条。

代价是与自选页的批量实现不相同构，无法直接复用其代码路径，只能复用其设施（`getPriceAt` 联动、`toDateTimeStr` 格式化、分组行内新建）。

### D6: 去重按 `(code, kl_type)` 保留最新，时间打平按级别强度

`monitor` 表没有 `(code, kl_type)` 唯一约束，`create_monitor` 也不查重，同一股票同一周期的两条监控会让监控列表出现两个重叠的跟踪窗口。因此提交前按 `(code, kl_type)` 去重、保留买卖点时间最新的一条，并在弹窗中告知去重前后的数量。

`bsp_index` 的唯一键含 `bsp_type`，同一根 K 线上可以同时存在如 `2` 与 `3b` 两条记录，故「最新」在一级键上会打平，需要次级裁决：按级别强度（L4 > L3 > L1 > L2）取强者，仍相同则按 `time_key` 倒序取首。用级别强度而非类型编号作为次级键，是因为级别承载的是「信号有多确定」，与用户在这个页面上的筛选意图一致。

### D7: 批量弹窗只留分组与只读清单

批量弹窗不提供可编辑的级别或起始时间，只提供分组选择（含下拉尾部行内新建）与本次待提交记录的只读清单（编码、名称、周期、买卖点时间、买卖点价格、方向）。分组必须保留——监控页的分组树依赖它作为唯一的人工分类输入。

列表里保留方向列是为了让「与行级同口径（含卖点行）」这个决定可自查：批量不拦截卖点行，用户需要能在提交前看到里面确实混着卖点。

不复用行级弹窗组件：行级弹窗有可编辑时间与价格联动，批量弹窗是只读清单，两者字段与状态差异较大，按 mode 分叉反而更难读——这与自选页的情况不同（其两种 mode 字段几乎一致，故可合并）。

### D8: 串行提交、部分失败不中断、成功后清空选择集

沿用自选页已确立的错误口径：逐条串行、单条失败不中断后续、完成后汇总成功与失败数，取价失败回退该行买卖点价格并计入失败。

额外增加一条：提交成功后清空选择集。自选页不清空，但批量监控是更敏感的操作——`monitor` 无唯一约束，重复提交会实打实产生重复监控行，清空是对误触的第二道防线。

## Risks / Trade-offs

- **`COALESCE` 表达式无法命中索引** → 当前 `bsp_index` 上没有 `ladder` 索引，执行计划与现状一致（都是顺序扫描），因此本次不引入回归；若数据量增长需要索引，应建**表达式索引**（对 `COALESCE(ladder, CASE ...)`）而非列索引。
- **按 `L1`/`L3` 筛选筛不到存量行** → 这是兜底映射值域决定的（存量行只能映射成 `L4`/`L2`），不是缺陷但容易被误读为数据缺失。缓解：spec 已写明该口径；页面是否加提示文案留作后续。
- **批量提交的请求数量** → 最坏每条 2 次串行请求（取价 + 创建）。当前 `page_size` 固定 20，但 `reserve-selection` 允许跨页累积，跨页多选时条数可能显著超过 20。缓解：提交期间弹窗整体 `v-loading` 并禁用确认按钮，避免重复提交；进一步优化见 Open Questions。
- **`BspRecord.id` 类型变更** → 已核实消费方仅 `BspView` 的 `row-key` 与 mock 数据，`NestingDrawer` 不读 `id`；风险集中在漏改 mock，导致 `VITE_USE_MOCK=true` 时表格出现重复 key 警告。
- **前端与后端需同时上线** → 前端开始发送 `ladder` 参数（旧后端会忽略之，表现为筛选静默失效）且依赖新的字符串 `id`（旧后端返回数字，`row-key` 仍可渲染，但跨查询串行问题仍在）。这不构成数据损坏，只需同步发布。
- **卖点行加入监控的语义** → 本次与行级保持同口径（不拦截），代价是用户可能对卖点建立「入场」监控。缓解：只读清单展示方向列。

## Migration Plan

- 无数据库变更：`bsp_index.ladder` 列已存在，本次只读取；`WebAPI/update-mac.sql` 与 `WebAPI/update-win.sql` 均无需追加。
- 无数据回填、无快照重建。
- 发布顺序：后端先行（新增 `ladder` 参数与稳定 `id`），前端随后。反向顺序下级别筛选静默失效，不报错。
- 回滚：回退前后端代码即可，无状态残留、无不可逆写入。

## Open Questions

- 级别下拉在实际 130px 宽度下的文案是否够用（拟用 L4 确认买卖点 / L3 背驰预警 / L1 区间套 / L2 虚笔候选，实测溢出再压缩）——纯前端文案问题，不影响 spec 与任务拆分。
- 跨页大量选中时是否值得把取价改为先并发、再串行提交，以缩短提交耗时——可延后，当前用 loading 态兜住体验。
