#### 任务 2.2：CChan 序列化方法

**目标**: 在 `Chan.py` 的 `CChan` 类上新增 `to_dict(kl_type: KL_TYPE) -> dict` 方法，按 design.md D2 契约导出 JSON。

**执行细节**:

1. 在 `CChan` 类末尾新增方法 `to_dict(self, kl_type: KL_TYPE) -> dict`:
   ```python
   def to_dict(self, kl_type: KL_TYPE) -> dict:
       """按 chan-web-viewer D2 契约序列化单级别缠论结果。"""
       kl_list = self[kl_type]
       # 权限检查、空值兜底...
   ```

2. 序列化各元素:
   - **K 线**: 遍历 `kl_list.klu_list`，逐个取 `klu.time.ts * 1000`（秒→毫秒）+ OHLCV
   - **笔**: 遍历 `kl_list.bi_list`，取 `get_begin_klu().time.ts * 1000` / `get_end_klu().time.ts * 1000` + `get_begin_val()` / `get_end_val()` + `dir` + `is_sure`
   - **线段**: 同笔结构，但源是 `kl_list.seg_list`
   - **笔中枢**: 遍历 `kl_list.zs_list`，取 `begin.time.ts * 1000` / `end.time.ts * 1000` + `low` / `high` / `mid`
   - **线段中枢**: 同中枢，源是 `kl_list.segzs_list`
   - **买卖点**: 遍历 `kl_list.bs_point_lst`，取 `klu.time.ts * 1000` + `klu.low if is_buy else klu.high` + `is_buy` + `[x.value for x in type]`

3. **关键实现注意**:
   - 需要导入 `KL_TYPE`（可能在 Common 或 ChanConfig）
   - 需要对 `None` 值做防御（如某个周期未加载）
   - 数量大时（如分钟线几万根）需考虑传输体积——阶段一先全量返回

4. 验证点: 写一段测试脚本，`CChan(code='sz.000001', config).to_dict(KL_TYPE.K_DAY)` 输出 JSON，确认时间戳为毫秒、笔端点为极值价。

**依赖**: 无（纯 chan.py 侧改动）

**预计修改文件**:
- `Chan.py`（新增方法）
- 可能的 util 辅助（如有需要）

### 🔴 Tier 3：计算服务与 PG 缓存（3个任务）

> **背景**: 这三个任务依赖 PG 存在和 chan.py 步进模式可行性，属于性能优化层。根据 design.md D8 和 D4，阶段一「先全量返回 K 线 + 缠论」，可暂时跳过 Tier 3，直接进入 Tier 4 联调。

---

#### 任务 3.1：PG 缓存表 + 稳定前缀

**目标**: 在 PostgreSQL 中建立 `chan_cache` 表，缓存已确认前缀的序列化 JSON。

**执行细节**:

1. 建表 SQL:
   ```sql
   CREATE TABLE IF NOT EXISTS chan_cache (
       id          SERIAL PRIMARY KEY,
       symbol      VARCHAR(20) NOT NULL,
       period      VARCHAR(10) NOT NULL,
       last_sure_ts BIGINT NOT NULL,         -- 最后已确认元素时间戳（毫秒）
       payload     JSONB NOT NULL,            -- 已确认前缀的序列化 JSON
       created_at  TIMESTAMPTZ DEFAULT NOW(),
       UNIQUE(symbol, period)
   );
   CREATE INDEX IF NOT EXISTS idx_chan_cache_lookup ON chan_cache(symbol, period);
   ```

2. PG 连接配置:
   - 从环境变量读取 DSN: `CHAN_PG_DSN`，格式 `host=... port=... dbname=... user=... password=...`
   - 若无 PG 可用，跳过缓存直接计算（不影响基本功能）

3. 缓存读取逻辑:
   - 查 `chan_cache WHERE symbol=? AND period=?`
   - 若有: 检查 `last_sure_ts` 是否与当前计算的最后已确认元素匹配
   - 匹配则直接返回缓存（零计算开销）
   - 不匹配则全量重算

4. 缓存写入逻辑:
   - 全量计算后，提取稳定前缀（所有 `is_sure == True` 的元素）
   - `UPSERT` 到 `chan_cache`

**依赖**: PG 数据库可用

**预计新增文件**:
- `WebAPI/cache.py`

#### 任务 3.2：Spike — 步进模式续算可行性验证

**目标**: 验证 open-source `CChan` 的 `trigger_step=True` 能否以「缓存前缀 + 新 K 线」为起点续算尾部。

**执行细节**:

1. 测试步骤:
   - 用 `trigger_step=False` 全量算一份 `sz.000001` 日线，记录笔/线段/中枢数量
   - 截断 K 线到前 80%，用 `trigger_step=True` 初始化
   - `trigger_load` 剩下 20% 的新 K 线
   - 对比最终笔/线段/中枢数量是否与全量结果一致

2. 两个可能结果:
   - **可行**: 步进模式续算结果与全量一致 → 记录验证通过，任务 3.3 可用
   - **不可行**: 结果不一致或抛异常 → 记录退化方案为「全量重算 + 仅缓存已确认前缀去重」

3. 验证脚本放在 `Debug/test_step_resume.py`

**依赖**: 无（纯验证，不写生产代码）

**预计新增文件**:
- `Debug/test_step_resume.py`

#### 任务 3.3：稳定前缀复用与失效

**目标**: 实现新 K 线落库时复用已确认前缀、只重算未确认尾部。

**执行细节**:

1. 流程:
   - 请求到达 → 查 PG 缓存
   - 若有缓存 → 加载 DuckDB K 线，只取 `timestamp > last_sure_ts` 的新 K 线
   - 以缓存前缀为起点，`trigger_load` 新 K 线
   - 提取计算结果中新的稳定前缀，UPSERT 回 PG

2. 失效条件:
   - 缓存不存在 → 全量重算
   - 新 K 线使某个已确认笔变成「必须包含处理」→ 退化全量重算
   - 手动传入 `?force_recompute=1` → 跳过缓存

3. 验证点: 两次查询同一 (symbol, period)，第二次确认命中缓存、计算时间显著降低。

**依赖**: 3.1（PG 缓存表）+ 3.2（步进续算可行）

**预计修改文件**:
- `WebAPI/cache.py`
- `WebAPI/router.py`

## 四、已知风险与注意事项

| 风险 | 影响任务 | 缓解措施 |
|------|----------|----------|
| DuckDB 中无 `sz.000001` 数据 | 2.4 | 先用灌数脚本灌一条日线 |
| PG 不可用 | 3.1/3.3 | 环境变量检测，无 PG 时跳过缓存直算 |
| 步进模式续算不可行 | 3.3 | 退化方案已在 3.2 中定义 |
| KLineChart `setLoadDataCallback` 与 v9.8 API 差异 | 5.3 | 查阅 klinecharts v9.8 docs 确认 API 签名 |
| 前端 API 路径 `/kline/:code` 与后端 RESTful `/klines/{code}` 细微差异 | 2.3/4.1 | 前端微调 `kline`→`klines` 即可，差异很小 |
| mock 数据的 period 参数支持 | 4.1 | mock handler 需从 query params 中读取 period |
